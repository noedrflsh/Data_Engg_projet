CONCEPT 1
The Central Fact Table

fact_ratings stores 32M numerical transactions. It contains only numbers (IDs, dates, ratings) to keep storage compact (3.7 GB).

CONCEPT 2
1NF Bridge Normalization

Instead of storing Adventure|Animation|Comedy as messy text, bridge_movie_genre links movie IDs to genre IDs for instant indexed joins.

CONCEPT 3
Precomputed Materialized Views

mv_movie_rating_stats pre-aggregates 32M ratings down to 84k rows, reducing leaderboard query times from 18 seconds to 0.6 ms.

Step-by-Step Journeys

3. Tracing the 3 Primary User Actions

Understand exactly what happens during Search, Dashboard Updates, and Rating Submission.

JOURNEY A • AUTOCOMPLETE SEARCH
Searching for a Movie

1. User types "Matrix" in the search box.
2. JavaScript waits 250ms after typing stops (debounce).
3. Sends GET /api/movies/search/?q=Matrix.
4. PostgreSQL runs indexed ILIKE search on dim_movies.
5. Returns matches in < 1 ms; dropdown renders.

JOURNEY B • ANALYTICS DASHBOARD
Selecting a Movie & Year

1. User clicks "The Matrix (1999)".
2. JavaScript fires 3 parallel requests for Tags, Details, and Rating Histogram.
3. Query hits idx_fact_ratings_movie_rating B-Tree index.
4. Runs an Index-Only Scan across 81,919 votes in 15 ms.
5. Chart.js smoothly animates and updates the visual panels.

JOURNEY C • PROBLEM 4 USER ACTION
Rating a Movie Live

1. User selects 4.5 ★ and clicks "Save Rating".
2. JavaScript sends POST /api/ratings/rate/.
3. Django enforces role permission and checks if user already voted.
4. Executes SQL UPSERT (inserts new or updates existing).
5. Browser shows green toast and refreshes the rating chart!

Performance Engineering

4. Why Queries Dropped from 18 Seconds to Sub-20 Milliseconds

Visualizing the physical disk difference between Sequential Scans, Covering B-Trees, and Materialized Views.

BEFORE OPTIMIZATION (18 SECONDS)
Sequential Table Scan

The hard drive must physically read all 450,000 disk blocks (3.7 GB) into memory, examining all 32,000,204 rows one by one.

WITH COVERING INDEX (15 MILLISECONDS)
Index-Only B-Tree Scan

PostgreSQL traverses a 3-level deep B-Tree index. It reads only ~30 blocks directly matching that movie, completely bypassing the 3.7 GB table!

WITH MATERIALIZED VIEW (0.6 MILLISECONDS)
Precomputed Summary Scan

Calculations like averages and counts are precomputed once on disk (11 MB). Answering *"Top 10 movies"* searches only 84,432 rows in 0.64 ms!
